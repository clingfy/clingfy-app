# Preparing a release (runbook)

How to **prepare** a Clingfy release. "Prepare" = everything up to (but not
including) firing the build/publish pipeline. **Building/signing/notarizing/
publishing a production release is done by a maintainer manually** (it needs
private credentials and a deliberate trigger) — see `ops/release/README.md` and
`docs/branching-strategy.md`. This runbook is the checklist to get a release
branch ready for that trigger.

> Written after preparing 1.0.5. If any step drifts, fix it here in the same PR.

## What a release touches

| Thing | File / place | Who sets it |
|---|---|---|
| Semantic version | `pubspec.yaml` `version: x.y.z+build` | **you** (prepare) |
| Build number | `pubspec.yaml` `+build` | you set a value; the pipeline's `ops/release/00_version_bump.sh` (`commands/version_bump.sh`) re-sets it to a CI build id at build time |
| Release notes / appcast source | `CHANGELOG.md` `## [x.y.z] - DATE` section | **you** (prepare) — extracted verbatim by `ops/release/lib/sparkle.sh` `extract_release_notes()` |
| Commit-history working set | `release_notes/` (`detailed-commits.md`, `shortlog.txt`, `ai-prompt.md`) | **you** — regenerated by `release_notes/release.sh`; **gitignored (local-only)**, used to *write* the CHANGELOG, not committed |
| Readiness checklist | `docs/releases/<x.y.z>/release-readiness.md` | **you** — copied from `docs/releases/TEMPLATE-release-readiness.md` |
| Tag `vx.y.z`, DMG, appcast, symbols | Azure / Sparkle | **pipeline** (maintainer fires it) |

## Steps

1. **Preconditions.** `develop` is green and stable, and every feature PR meant
   for this release is merged. Decide the version — the convention so far is a
   **patch bump** even for big features (1.0.2 pause/resume, 1.0.3 zoom editing,
   1.0.4 backgrounds, 1.0.5 clips+color were all patch bumps). Check
   `git tag --sort=-v:refname` for the latest.

2. **Cut the release branch from develop** (branching strategy uses a short-lived
   stabilization branch; `ops/release/00_version_guard.sh` later checks the branch
   name matches the pubspec semver):
   ```bash
   git checkout develop && git pull --ff-only origin develop
   git checkout -b release/x.y.z
   ```

3. **Bump `pubspec.yaml`** to `x.y.z+<build>` (increment both; the pipeline may
   overwrite the build number with a CI id — that's expected):
   ```bash
   sed -i '' 's/^version: .*/version: x.y.z+<build>/' pubspec.yaml
   ```

4. **Regenerate `release_notes/`** so it covers this window. Point the script at
   the *previous* release tag's commit, then run it. **`release_notes/` is
   gitignored** — it's a local working set to source the CHANGELOG from, not
   committed:
   ```bash
   PREV=$(git rev-list -n1 v<prev>)          # e.g. v1.0.4
   sed -i '' "s|^START_COMMIT=.*|START_COMMIT=\"$PREV\"|" release_notes/release.sh
   bash release_notes/release.sh              # -> detailed-commits.md, shortlog.txt, ai-prompt.md
   ```
   Use `release_notes/ai-prompt.md` as the grouping spec + `detailed-commits.md` /
   `shortlog.txt` as the source when writing the CHANGELOG.

5. **Write the `CHANGELOG.md` entry.** Prepend a section above the previous one:
   ```
   ## [x.y.z] - YYYY-MM-DD
   <one-paragraph summary>
   ### Highlights / New Features / Improvements / Bug Fixes / Refactoring / Docs
   ```
   - **The `## [x.y.z] - DATE` heading format is load-bearing** — `sparkle.sh`
     matches `^## \[x.y.z\]` and extracts everything up to the next `## [`. Verify:
     ```bash
     awk -v v="x.y.z" 'BEGIN{s=0} $0~"^## \\["v"\\]"{s=1;next} s&&$0~"^## \\["{exit} s{print}' CHANGELOG.md
     ```
   - **Focus on macOS user-facing changes** (this is the updater's release note).
     The Windows-port commits are internal/beta — a one-line mention in
     "Refactoring / Internal" is enough, not a per-phase list. Rewrite technical
     commit subjects into user language; merge related PRs into one bullet.

6. **Create the readiness checklist:**
   ```bash
   mkdir -p docs/releases/x.y.z
   cp docs/releases/TEMPLATE-release-readiness.md docs/releases/x.y.z/release-readiness.md
   ```
   Fill the **Release Metadata** block (Version `vx.y.z`, Channel `prod`, Date,
   Verified by, Tag `vx.y.z`, Status `In progress`; Commit/Build filled at build).

7. **Commit on the release branch and push.** Do **not** fire the pipeline and do
   **not** auto-merge the release branch (release branches are special — they
   merge back after a *successful build*, unlike feature PRs). Suggested commit:
   `chore(release): prepare x.y.z (version bump + changelog + readiness)`.

8. **Hand off to the maintainer.** They run the pipeline (`ops/release/` — build →
   notarize → dmg → publish appcast → git tag; Windows lane under
   `ops/release/windows/`). After a green build they mark the readiness
   `Approved`/`Released`, and the `release/x.y.z` branch **rebase-merges into both
   `main` and `develop`** (per `docs/branching-strategy.md`).

## Gotchas

- **CHANGELOG heading format** must be exactly `## [x.y.z] - YYYY-MM-DD` or the
  appcast falls back to "Bug fixes and performance improvements".
- **Build number** you set is a placeholder; `version_bump.sh` overwrites it with
  `current_build_id()` at build time. Set a sane one anyway (prev + 1).
- **Don't fire the pipeline** — it needs private signing/notary/Azure creds the
  repo intentionally does not hold; only the maintainer triggers it.
- **Release branch ≠ feature PR** for the auto-merge rule — leave it for the
  post-build merge-back.
- Keep the `bridge_contract_coverage` and platform smoke checklists honest if the
  release touched the native surface.
